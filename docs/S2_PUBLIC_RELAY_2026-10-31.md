# OpenKinGuard S2：公网中继基础 / 自建节点（2026-10-31）

## 本阶段代码已实现的范围

- 统一 Android APK 中的**可选** `wss://.../relay` 自定义中继地址、启停与连接状态；默认关闭。不依赖 Google Play 服务，不引入中央账号。
- 中继服务端 Python 3.10+、`websockets`、`cryptography`；单进程实时转发。**0.5.1 起可选择在内存中短暂排队测试 SOS/报平安**（有数量与5分钟上限，重启即丢失），仍不会写磁盘。默认只监听 `127.0.0.1:8765`，必须由 Caddy / Nginx 等可信 TLS 反向代理暴露 `wss://.../relay`；如直接暴露，则必须 `--cert` 和 `--key` 启动 TLS。
- Android Keystore 中原有 P-256 设备私钥签署服务器随机挑战。中继只接受验签成功的设备公钥指纹，并给每个在线指纹唯一会话；客户端确认返回的指纹为本人。中继不能自行伪造现有应用层签名。
- 已绑定设备间的签名 PING/昵称同步、SOS 测试、接手/结案、报平安、按关系授权的手动定位请求可以借同一中继交换；接收方仍通过现有签名、关系、授权、重放校验路径，精确 GPS 回执仍采用请求专属 ECDH + AES-GCM。
- 优先已有的局域网认证 TCP；局域网不可达时可尝试**用户主动启用**的公网中继。服务端返回离线、超时、拥堵等原因；对方拒绝时不会泄漏具体敏感授权状态。
- 支持活动期间 WebSocket 心跳与断线重连。只有 App 前台，或由用户开启既有前台服务时，才尝试维持连接；系统清理、强制停止、运营商网络切换等不能保证保持在线。

## 电脑部署（建议首先用电脑测试）

1. 在有公网可达入口的电脑或 WSL/Ubuntu 运行：

   ```bash
   cd OpenKinGuard
   python3 -m venv .venv
   . .venv/bin/activate
   pip install -r relay/requirements.txt
   python3 relay/openkinguard_relay.py --listen 127.0.0.1 --port 8765
   ```

2. DNS 指向你的可到达 IPv4/IPv6 公网地址（可动态 DDNS）；通过可信 TLS 代理转发：示例 `relay/Caddyfile.example`。修改其中 `relay.example.cn`，在 Caddy 所在电脑开放 TCP/443 和证书申请所需入口，代理回环端口 8765。Android 填 `wss://relay.example.cn/relay`，**不要填写** `ws://`、`http://` 或内网 `192.168.*` 地址。
3. 两台已绑定 Android 10+ 手机在 **设置 → 公网通信·自建中继** 中填写同一地址，分别“保存并启用”。0.5.1 起可每行填写一个地址，最多三个；两端至少有一个共同连通的中继。等两端显示身份连接成功，再尝试签名在线认证、报平安、SOS 测试或定位授权请求。无需重新扫码绑定。
4. 若 Windows 防火墙、路由器端口映射、运营商 CGNAT、证书 DNS 校验或双栈不通，中继无法从移动公网连接。此处不替用户修改路由器防火墙和端口映射。

Linux 服务器可参照 `relay/openkinguard-relay.service.example` 设置 `systemd` 开机自启（须先建立专用用户及实际路径）。**Windows/WSL 只有电脑开机、WSL 实际运行并且网络服务已启动时才在线**，不能把 WSL 的进程误认为天然 24 小时守护进程。

## OpenWrt 路由器节点

- 若你的 OpenWrt 设备有足够闪存/扩展存储和 RAM，而且**其软件仓库中能安装对应 Python 解释器以及 `websockets` 和 `cryptography` 包**，可以运行相同的 `relay/openkinguard_relay.py`。不同 CPU/固件架构的 Python 加密依赖可能不可用，不能把它当作“任何路由器都可直接安装”。
- **推荐混合方案**：OpenWrt 负责 DDNS、防火墙和 TCP/443 转发至电脑；电脑上运行 Caddy（HTTPS/WSS）及仅监听 `127.0.0.1:8765` 的 Python 中继。电脑关机则中继不可用。若 Caddy 直接在 OpenWrt 上运行，其后端必须指向**可从路由器访问的电脑内网地址**，不能指向路由器自身的 `127.0.0.1`；这种跨机后端应再加 TLS/可信局域网隔离。路由器独立承担中继时，可将 Python 与 Caddy 都部署在路由器自身（取决于依赖及存储）。后续可开发占用更低的原生守护进程。
- 只有公网 IPv6 的家庭节点，需要确认**两台手机实际网络都能访问 IPv6**。只有运营商内网 IPv4、又没有可到达 IPv6 时，无法让手机从外网直接访问；应换可达节点或使用合规云主机/中继。

## 必须明确的限制

1. **本版是可运行的通信基础，不是已部署的公共服务。** 服务端本地自动测试通过，但 Android 10/17 两机跨公网完整链路仍需用户测试，不能用于真实救援。
2. 中继能观察联网设备公钥指纹、时序、包长与消息元信息。**普通 SOS 与报平安消息当前只有应用签名，没有完整端到端加密**；精确 GPS 坐标另有单次端到端加密。后续版本需对所有消息统一加密。
3. 0.5.1 中继支持用户自愿启用的**测试 SOS/报平安 RAM 暂存（最多5分钟）**，仍不保证离线投递：服务端重启、内存排队过期、目标未连接原节点、被操作系统杀死均可能丢失；**暂存不等于签名送达确认**。GPS 定位请求不进入队列。手机前台或用户开启的系统前台服务能改善收件概率，但 Android 省电/网络限制仍会暂停。
4. 此阶段没有 NAT 穿透 P2P（ICE/STUN/TURN）、公开可替换中继列表自动发现、全站消息加密、远端撤销同步或高可用多节点切换。仍保留将来优先 P2P 的规划，不把单台家庭中继宣称为可靠基础设施。
5. 正式公网上线前，应审查并落实 TLS、访问滥用防护、运营商/当地合规要求和家庭网络隔离；不要将 OpenWrt 管理后台暴露公网。

## 自检

在项目根目录运行（自动开启仅回环本机随机端口）：

```bash
python3 -m unittest discover -s relay -p 'test_*.py' -v
```

验证服务端身份挑战、不可伪造回复、离线状态、过大报文限制及两设备转发。
