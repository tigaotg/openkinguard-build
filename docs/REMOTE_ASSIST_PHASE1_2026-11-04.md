# OpenKinGuard 远程协助 · 第一阶段（仅源码，未编译）

## 目标与边界

- 唯一客户端，双方可同时拥有监护和被监护角色。
- 监护端只能向已经建立有效 `HELPER -> SUBJECT` 互助关系的设备申请。
- 每次申请都必须被监护端本人点击「同意协助」。已经绑定不代表可远程控制。
- 请求有效期 60 秒；本地同意仅进入 `AWAITING_SCREEN_PERMISSION`，不自动录屏。
- 取消、拒绝、超时、进程重启均清除内存授权；本机停止无须等到网络成功。
- 不修改既有 SOS/报平安业务数据、设备密钥、设备配对及定位授权。

## 已实现：控制信令（不是远程桌面）

1. 新增 `RemoteAssistWire`，定义 `REQUEST / ACCEPT / DECLINE / STOP / RECEIPT`。
2. 所有信令走原有已绑定设备的签名消息格式和 `LAN -> UDP P2P -> 私人中继` 选择路径。
3. 通过 `AuthenticatedAdmission` 验证设备公钥、关系和防重放窗口。
4. 新增 `RemoteAssistConsent`：前台弹窗、人工决定、会话超时与撤销。
5. 在线设备操作项新增「请求远程协助 · 连接测试」。
6. 新增小型协议测试和人工同意状态测试。

## 尚未实现，不得向使用者称为可远程控制

- `MediaProjection` 的系统录屏授权以及 Android 14+ 每次会话授权。
- 持续的低延时视频编码/解码、帧丢弃与速率控制。
- WebRTC/ICE/DTLS-SRTP 或同等安全的专用媒体通道。
- `AccessibilityService` 手动开启与可见的远程手势/文本控制。
- 被协助端的常驻提示、随时停止入口、断网清理和受保护应用遮挡。
- NAT 无法打洞时的媒体中继（原有公共 Nostr 节点只负责发现，不转发视频）。

## 已核实的现有 P2P 限制

`S5DirectUdp` 为带 STUN 的实验性 UDP 信令/短包请求-回执方案。
`request()` 将应用数据限制为 100–6800 字节，每个请求存在超时与并发限制；
不是可直接复用来发送连续视频流的 WebRTC 通道。
因此后续应该保留现有候选交换、设备身份与签名短消息，独立引入媒体层，
而不能把屏幕画面写入 SOS 消息、公共 Nostr 节点或原有短包队列。

## 下一阶段入口设计

1. 老人点击「同意」后才可启动系统 `MediaProjection` 许可流程；用户取消即终止。
2. 仅在系统授权后启动可见前台服务，推送加密视频到指定绑定会话。
3. 用户在系统设置中手动启用无障碍服务后，才允许独立签名授权的手势。
4. 服务端使用会话 ID、对端设备指纹、单次授权 token、过期时间绑定每帧控制输入。
5. 进入后台/锁屏/录屏停止/网络切换/关系撤销/SOS 高优先级事件时，
   远程控制立即安全暂停或关闭；任何失败均不得影响原有报警通道。
