# OpenKinGuard 0.4.3 · 主页设备操作、厂商查找关联和昵称刷新

版本：`versionCode=18`、`versionName=0.4.3-home-device-actions`，最低 Android 10。调试包名、签名身份和已有配对公钥不变；本次没有要求用户卸载旧应用。

## 交互改动

- 底部主导航只有「求助」和「设置」。主页会列出每一台已绑定设备的 **验签** 局域网心跳状态，区分最近在线、等待心跳、超过3分钟、超过10分钟和未确认在线。仅 mDNS 发现不能证明对方在线，更不能证明对方本人安全。
- 本机是救助者时，该被救助设备卡片有「请求定位」按钮；仅签名验证在线时允许点击，远端仍必须单独授权位置、开启系统权限、保持前台。失败原因沿用现有可读提示。
- 本机是被救助者时，对应救助设备卡片有「报平安给此设备」，新建报平安记录包含明确的目标关系 ID，重试时仅对该关系送达，不会错误群发。原主页「我平安 · 通知救助者」仍按原意向所有救助者广播；新记录仍会取代同一设备的旧类事件，历史不删除。
- 设备卡片附「厂商查找」；用户须在「设置 → 设备与授权」逐台指定内置官方 HTTPS 查找网址。配置按**已绑定的公钥指纹**保存，两个角色指向同一台手机时共用一个入口。尚未指定时提示进入设置，不猜测厂商；网址仅交给系统浏览器，OpenKinGuard 不读取厂家账号、密码或查找结果，也不会因此获得远程定位权限。
- 在设置首页进入「设备与授权 · 连接新设备」管理昵称、定位授权、绑定、撤销和每台厂商入口；「历史记录与请求」可继续切换当前/归档 SOS、报平安、定位及操作结果。系统后台连接、通知、病历文件夹等仍在设置页面。
- 原有下拉刷新、故障反馈、单一主页 SOS 卡片、记录加密保留天数和本机病历入口保持不变。

## 昵称刷新缺陷

**已发现症结**：发现列表对之前验签的设备优先读取本机 `peerNicknames` 旧备注，这会挡住本次 mDNS 广播中的新昵称；进行中的帮助邀请也会复制邀请开始时的昵称。

- 发现列表优先显示当前广播昵称，并明确「未经身份验证」，同时单独显示已验签昵称；对旧的本机自定义备注不做静默删除。
- 发起帮助邀请后，若在同一 IP 发现更新的广播昵称，待确认页会使用新昵称。广播仍不作为身份凭证。
- 自己修改昵称后重新注册 mDNS 服务时更换随机服务实例名，促使 Android 重新发现；现有公钥、帮助关系和会话 ID 不变。与已绑定设备的签名资料交互仍会把经过验签的新名字写回本机缓存。
- 旧系统可能继续缓存旧记录，广播刷新也可能失败；不能保证任何厂商 ROM 立即显示新昵称。要以验签昵称与指纹、安全码为绑定依据。

## 安全性和待测项

- 厂商 URL 必须匹配代码内置 HTTPS 白名单；保存在既有本机 AES-GCM 加密状态中。选择厂商只是一条浏览器快捷方式。
- 单机报平安仅选已存在的 `SUBJECT` 方向关系；旧版文件里没有目标字段的记录兼容解释为向全部已授权救助者报平安。
- 本轮只有 JVM 测试、编译、静态检查等自动验证。**用户明确表示暂不双机实测**。需复测 Android 10 和 Android 17 的主页状态更新、单设备报平安、设置入口、厂商浏览器调用、昵称变更后的发现和关联、后台网络恢复与定位失败提示。
- 当前仅局域网演练。没有互联网中继、可靠跨网 SOS、真实后台连续 GPS、心率监测、自动救援短信电话；不要作为医疗或人身安全保障。
